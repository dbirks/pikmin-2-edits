## Format grammar (measured, ADR-0016)

```
# CaveInfo
{
        {c000} 4 34       # <Shift-JIS comment>
        {_eof}
}
34 # FloorInfo
{
        {f008} -1 1_units_tower_toy.txt     # resource to use
        {_eof}
}
```
* Sections repeat: one file can hold many `# CaveInfo` / `# FloorInfo` blocks.
* A section header may carry a **numeric prefix** (`34 # FloorInfo`). **The prefix
  is NOT the row count** — measured: `Dam_cave_conc.txt` declares 2 and holds 15
  floor rows; `caveinfo.txt`'s first FloorInfo block declares 34 and holds 19.
  Meaning unresolved; do not gate a build on `declared == rows`.
* The only invariant that held across all 328 FloorInfo blocks in all 85 files:
  each block ends with `{_eof}`. That is what `check_floor_counts().ok` asserts.
* Field types seen: `4` (int), `-1` (string path), and floats printed inside
  `4`-tagged fields (`4 0.000000`).

## Rules the compile step must respect (from AGENTS.md + this survey)

1. Reuse an existing slot; do not mint new cave IDs or resources yet.
2. Never change a floor row's *count* without the matching `f008`/`f009`
   resources existing in the tree — that is the black-screen generator.
3. Edits are in-place substring patches (`cavedata.patch_text`), never
   re-serialised files: re-serialising dropped `{`/`}` lines and header prefixes.
4. Preserve Shift-JIS encoding, CRLF, tab indentation and trailing spaces
   (a test now pins that a no-op patch returns byte-identical bytes).
5. Validate references + block termination statically *before* repacking; a
   passing validator is not an in-game pass (separate lanes).
